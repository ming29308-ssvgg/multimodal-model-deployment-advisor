# 模型候选对比增强设计

## 意图

让推荐接口不只返回一个模型名称，而是针对每个任务阶段输出多个具体型号及可对比的部署配置，并结合自动检测到的硬件说明为什么推荐、为什么勉强可用或为什么不适合本地部署。

## 目标

- 每个模型阶段默认返回最多 3 个候选，用户可通过现有参数调整为 1～5 个。
- 候选包含参数规模、量化、最低/推荐显存、最低内存、预计本机显存占用、运行框架和部署命令。
- 候选包含硬件解释、优势、代价和不适配原因。
- 首选、质量优先、速度优先和服务器候选可以同时出现在结果中。
- 扩充文本、代码、视觉、OCR、语音识别、语音合成、图片生成、视频理解和视频生成目录。
- 保持现有 API 路径和请求结构兼容。

## 非目标

- 不下载或启动模型。
- 不承诺资源估算等同于实际基准测试。
- 不在第一版实现在线模型市场同步。

## 返回结构

`CandidateRecommendation` 增加：

- `parameter_size`
- `quantization`
- `min_vram_gb`
- `recommended_vram_gb`
- `estimated_vram_gb`
- `min_ram_gb`
- `hardware_reasons`
- `tradeoffs`

现有 `model_id`、`score`、`fit_tier`、`recommended_runtime`、`deployment_command` 和 `warnings` 保持不变。

## 推荐解释规则

- 明确比较本机总显存、当前可用显存和模型最低/推荐显存。
- 明确比较系统总内存和模型最低内存。
- 已安装运行时应成为加分理由；未安装应成为警告。
- `ideal` 表示当前可用资源直接满足；`runnable` 表示总资源满足；`constrained` 表示需要释放资源、量化或 Offload；`unsupported` 表示应使用更大服务器或远端服务。
- 较大模型强调质量优势和速度/资源代价，较小模型强调速度和余量。

## 方案

采用本地数据驱动目录。模型数据继续存放在 `models.json`，匹配器负责把静态配置与实时硬件组合成解释性结果。相比在节点中硬编码说明，该方式更容易扩充模型，也保持 LangGraph 节点职责清晰。
